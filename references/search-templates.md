# 检索模板：业界方法 + GitHub 现成实现

本文件只规定「怎么查、怎么判、怎么记」，不包含任何检索结果；文中查询语句都是待填槽位的模板，阈值数字只是参数。

**来源纪律**：检索产出必须带 `[web:URL]` / `[GH:owner/repo]` 标签与证据强度；凭经验写下的判断一律标 `[先验]`。

**前置**：先把「问题（一句话，含领域词）／成功标准（可验证）／不做（边界）」写清，关键词由这三项推导。

## 1. 业界方法（web）：三段式关键词

同一问题域按三段各跑一次，它们回答三个不同问题：

| 段 | 关键词模板 | 回答的问题 | 产出流向 |
|----|-----------|-----------|---------|
| 做法 | `{领域词} {动作} best practice` | 有没有成熟做法 | 前车之鉴条目 |
| 坑 | `{领域词} {动作} pitfalls` | 哪里会翻车 | 前车之鉴条目 |
| 取舍 | `{领域词} {方案A} {方案B} tradeoff` | 路线之间付出什么代价 | 候选流程的风险列 |

只跑「做法」段，等于只查「怎么做」不查「哪里会翻车」，是明确的失败模式（见 `failure-patterns.md`）。

四条可直接套用的模板：

```text
# T1 技术实现（中）
{技术栈} {要实现的能力} 最佳实践
{技术栈} {要实现的能力} 常见坑
{技术栈} {方案A} {方案B} 对比 取舍

# T2 技术实现（英）
{tech} {capability} best practice
{tech} {capability} pitfalls
{tech} {optionA} vs {optionB} tradeoff

# T3 排障（报错原文逐字加引号）
"{完整报错原文}"
"{报错核心句}" {技术栈}
"{报错核心句}" workaround OR issue

# T4 流程 / 选型（中英混合）
{任务类型} workflow best practice
{任务类型} process pitfalls
{自研方案} vs {复用现成实现} tradeoff
```

- T3 的关键是逐字引号：保留报错原有符号与数字，不翻译成自然语言；太长时取最能定位的连续半句，仍要加引号——不加引号会被拆词，召回退化成泛搜。

**关键词构造规则**：

- 领域词优先取用户原话里的名词，再补上位词与同义词，不要自创术语；一条 query 只问一个问题，「做法描述」与「可执行方案」分开记（前者只影响判断，后者才可能进候选流程）；语种轮次见第 6 节

## 2. GitHub 检索（主检索地）

GitHub 是主检索地：要的是「能拿来用的现成实现 / 现成 skill」，不是方法论综述。

基础模板：

| 目的 | 模板 |
|------|------|
| 找 skill 形态的项目 | `site:github.com {关键词} skill` |
| 找 SKILL.md 形态的说明 | `site:github.com {关键词} SKILL.md` |
| 找现成实现 | `site:github.com {关键词} {技术栈}` |
| 找同类项目汇总 | `site:github.com {关键词} {领域} 清单` |

限定符：

| 限定符 | 写法示例 | 作用 | 何时用 |
|--------|---------|------|--------|
| `topic:` | `topic:{领域标签}` | 按仓库话题过滤 | 已知该领域 topic 名时 |
| `language:` | `language:{语言}` | 按主语言过滤 | 技术栈已定 |
| `stars:` | `stars:>{阈值}` | 按采用度过滤 | 只要有一定使用面的仓库 |
| `pushed:` | `pushed:>{YYYY-MM-DD}` | 按最后推送时间过滤 | 排除停更仓库 |
| `in:readme` | `{关键词} in:readme` | 限定在 README | 关键词太泛、噪声大时 |
| `path:` | `path:SKILL.md {关键词}` | 限定文件路径 | 精准定位 skill 说明文件 |

- 阈值和日期是参数，按当前任务填，不代表任何检索结果；一次最多组合两个限定符（叠三个以上召回急剧变窄，先放宽再逐步收紧）；组合示例：`site:github.com {关键词} skill pushed:>{YYYY-MM-DD} stars:>{阈值}`、`site:github.com {关键词} SKILL.md path:SKILL.md`、`site:github.com {关键词} topic:{领域标签} language:{语言}`

## 3. 命中判定表

拿到一个仓库，先判档，再决定它能用到哪一层：

| 判定 | 判定标准（逐项过） | 允许用在哪 |
|------|-------------------|-----------|
| 可直接用 | 覆盖成功标准主要项；依赖规模同量级；近期仍有推送；证据强度为正文已读；许可证兼容；无明显安全告警 | 候选流程 A/B 的主干 |
| 需改造 | 主干思路可用，但接口 / 依赖 / 规模不匹配；仍在维护；缺的是适配层 | 候选主干，并写明改哪一部分 |
| 仅作参考 | 停更、依赖过重、规模差一个量级、许可不明、只覆盖边角、证据只到标题或摘要 | 只能进「前车之鉴」条目，不得做候选主干 |

判定必看的四要素（任一不过即降档）：

| 要素 | 看什么 | 不通过时 |
|------|--------|---------|
| 维护活跃度 | 最后推送时间、issue/PR 是否有回应（本次实际看到的才算） | 降为「仅作参考」 |
| 依赖规模 | 新增几个依赖、是否拖进整套框架 | 降档或淘汰 |
| 覆盖成功标准 | 逐条对照成功标准打勾，不按「看起来像」判断 | 打不满就不能判「可直接用」 |
| 许可与安全 | 许可证是否兼容、有无需留意的告警 | 许可不明 → 淘汰或进 open questions |

**判定必须能回答「我凭什么这么判」**：凭本次实际看到的 README、文件、提交记录，不凭仓库名或第一印象。证据只到标题或摘要时不得判「可直接用」，降为「需改造」或「仅作参考」并写明强度。

## 4. 命中记录格式

一个命中一行，固定格式（证据强度不可省）：

```text
[GH:{owner}/{repo}] — {可直接用|需改造|仅作参考} — 证据强度：{正文已读|仅标题|仅摘要} — 一句话用途
[web:{URL}] — 证据强度：{正文已读|仅标题|仅摘要} — 一句话用途 + 关键结论
```

- 证据强度只到「仅标题 / 仅摘要」的，不得支撑「可直接用」，且结论里要写出来（例：按标题判断，未读正文）
- `{owner}/{repo}` / `{URL}` 必须替换为本次真实检索到的对象，没检索到的一律不写；同一仓库只记一行，同类只记判定最高的一两个，记录与「前车之鉴」条目分开放
- 判定栏只允许三种值；写「比较合适」这类模糊词视为未判定

## 5. 低成本核验仓库

以下均为 `[先验]` 操作提示，不是检索证据；核验得到的事实仍按 `[web:URL]`（本次真实取到的页面）或 `[GH:owner/repo]`（本次真实查到的仓库）记录，并注明证据强度。

仓库页只回导航壳、抓不到正文时，用下面这些方式低成本拿事实：

- raw README：`raw.githubusercontent.com/{owner}/{repo}/HEAD/README.md`，HEAD 免查默认分支名，一次拿全文
- 仓库元数据：`api.github.com/repos/{owner}/{repo}`，看 `pushed_at`（维护活跃度）、`license`（许可），对应判定四要素中的两项；星数只作采用度参考，不单独构成判定
- 维护状态：`api.github.com/repos/{owner}/{repo}/issues?state=all`，看最近 issue/PR 是否有回应
- 抓取失败或只拿到标题：证据强度记「仅标题」，判定降档，未核项写进 open questions，不要反复重试同一抓取
- 这类核验属「读正文」，不新增检索次数；但只允许核验本次已命中的仓库，不得借核验开新方向

## 6. 检索预算（硬上限）

| 档位 | web 检索 | GitHub 检索 | 前车之鉴条目 | 收敛后 |
|------|---------|------------|------------|--------|
| fast | 0 | ≤1 | ≤3 | 1-2 |
| standard | ≤3 | ≤2 | ≤5 | ≤3 |
| deep | ≤6 | ≤4 | ≤5 | ≤3 |

- 计数口径：一条 query 计一次；一次工具调用带 N 条 query 记 N 次；不得把多条 query 合并成一次来凑数
- 读正文：web_fetch 只用于读「本次检索已命中」的页面，属读正文，不单列检索次数；抓取本次未命中过的新页面 ＝ 新检索，要占预算，不得用 fetch 绕预算
- 语种轮次：standard 默认单语种（通常英文，覆盖规范与讨论）；deep 才中英各一轮（英文查规范与讨论，中文查本土实践）；轮次与读正文都不得突破本档预算
- 预算耗尽即停，未查清写进 open questions；fast 档 web 为 0 是不查、不是少查（fast 只跑 1 次 GitHub）；不得为凑条数重复查

## 7. 检索无果的正确写法

无果不是失败；把「没查到」写成「不存在」才是失败。固定句式：

```text
- 未能检索到 <具体方向> 的可用方案 [未检索到]
- 关于 <问题> 的业界做法，本次检索无可靠来源，见 open questions
```

尖括号处填具体方向或问题，其余字符照抄；「未检索到」是标签，不是修辞。

## 8. 落盘前自查与常见错误写法

| 错误写法 | 错在哪 | 正确写法 |
|---------|--------|---------|
| 没有现成方案 | 把「没查到」说成「不存在」 | 本次未检索到可用方案 [未检索到] |
| 某项目很流行，可以借用 | 无标签、无判定、无证据强度 | `[GH:{owner}/{repo}]` — 需改造 — 证据强度：仅标题 — 借其主干 |
| 应该有个库能做这个 | 印象当事实 | 写进 open questions，标 [未验证] |
| 参考了一些开源实践 | 来源不可审计 | 逐条给 `[web:URL]` / `[GH:owner/repo]`，给不出就删 |

- [ ] 每条检索记录都有来源标签与证据强度，且是本次真实检索到的；没有编造的 owner/repo、URL、版本号、star 数、日期
- [ ] 判定栏只有三种值且能说出判定依据；证据强度只到标题 / 摘要的没有被判「可直接用」
- [ ] 检索次数（含语种轮次与 fetch 抓新页面）未超当前档位预算
- [ ] 无果的检索按第 7 节写法落成「未检索到」而非「不存在」；检索结果必须改变至少一个决策，一条都没改变 → 整份记录删除
